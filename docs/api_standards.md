# MBC WalkWith API Standards

Status: draft  
Audience: backend, mobile, admin web, future user web, integrations

This document defines the **cross-cutting standards** that apply to every API
surface in this repository.

Use this document as the canonical source for:

- route and versioning conventions
- request and response envelopes
- authentication and authorization rules
- signing and signature verification rules
- idempotency, pagination, timestamps, money, and error handling

`docs/api.md` may describe endpoint-by-endpoint behavior, but this document
takes precedence for shared rules.

## 1. Scope

These standards apply to:

- public mobile-facing REST APIs
- member-authenticated APIs
- admin APIs
- server-to-server webhook endpoints
- future internal service callbacks

They do **not** apply to:

- raw database contracts
- backend scheduler/internal function calls
- local-only mock data

## 2. API Classification

All APIs must belong to one of these classes:

```text
public
member
admin
server_to_server
internal
```

Definitions:

- `public`: readable without login
- `member`: requires member authentication
- `admin`: requires admin authentication and RBAC
- `server_to_server`: called by third-party systems such as payment/webhook providers
- `internal`: non-public callbacks between trusted backend components

## 3. Versioning and Base Paths

Rules:

- All externally callable APIs must be versioned under `/v1`.
- Breaking changes require a new version prefix.
- Do not mix admin and member concerns under the same base path.

Required path layout:

```text
/v1/health
/v1/settings/public
/v1/sermons
/v1/life/posts
/v1/member/auth/*
/v1/member/*
/v1/admin/*
/v1/webhooks/*
```

Examples:

```text
GET  /v1/sermons
POST /v1/member/auth/login
PUT  /v1/member/devices/push-token
POST /v1/admin/sermons/:sermonId/publish
POST /v1/webhooks/giving/stripe
```

## 4. Transport and Content Rules

Rules:

- HTTPS only outside local development.
- JSON is the default request and response format.
- `Content-Type: application/json` for JSON bodies.
- Binary upload endpoints must explicitly document accepted content types.
- Timestamps must be ISO 8601 UTC strings.
- Money must use minor units such as `amountCents`.

Examples:

```json
{
  "createdAt": "2026-05-22T19:30:00Z",
  "amountCents": 5000,
  "currency": "USD"
}
```

## 5. Common Headers

Recommended headers for app/admin clients:

```text
Authorization: Bearer <token>
Accept-Language: zh-Hans
Content-Type: application/json
X-Client-Platform: ios | android | web | admin
X-Client-Version: 1.0.0
X-Request-Id: <uuid-or-stable-request-id>
Idempotency-Key: <uuid>        // required on selected mutation endpoints
```

Rules:

- `Authorization` is optional for public endpoints and required for protected endpoints.
- `X-Request-Id` should be generated by the client when possible.
- `Idempotency-Key` is required for payment creation, statement generation,
  provider-triggered reconciliation, and any endpoint where retry duplicates are unsafe.

## 6. Request/Response Envelope

Success envelope:

```json
{
  "data": {},
  "meta": {}
}
```

List envelope:

```json
{
  "data": {
    "items": []
  },
  "meta": {
    "pagination": {
      "limit": 20,
      "nextCursor": null
    }
  }
}
```

Rules:

- Do not return top-level arrays for externally consumed APIs.
- `meta.pagination` is required for cursor-paginated list endpoints.
- `meta` may be empty but should remain present for shape stability when useful.

## 7. Error Contract

All errors must return:

```json
{
  "error": {
    "code": "validation_failed",
    "category": "validation_error",
    "sourceLayer": "surface",
    "message": "Request validation failed.",
    "recoverable": true,
    "retryable": false,
    "evidence": {
      "requestId": "8e9426d7-1b74-4988-a62e-2f58720f5d31"
    },
    "nextAction": "review_request",
    "details": {}
  },
  "requestId": "8e9426d7-1b74-4988-a62e-2f58720f5d31"
}
```

Standard error codes:

```text
bad_request
auth_required
forbidden
not_found
validation_failed
rate_limited
invalid_code
code_expired
challenge_consumed
challenge_not_found
idempotency_conflict
signature_invalid
event_capacity_full
statement_not_ready
checkout_session_failed
webhook_signature_invalid
sermon_not_found
media_missing
object_upload_failed
notification_provider_unavailable
job_cancel_invalid_state
internal_error
```

Rules:

- `message` must be safe for end-user display unless the endpoint is explicitly internal.
- `details` may include structured validation info but must not leak secrets.
- `category` classifies the failure, for example `validation_error`,
  `authentication_required`, `permission_denied`, `not_found`,
  `state_conflict`, `external_dependency_failed`, or `configuration_missing`.
- `sourceLayer` identifies the owner layer: `surface`, `feature`, `domain`,
  `capability`, `repository`, `external`, or `unknown`.
- `recoverable`, `retryable`, and `nextAction` must be preserved by SDK and UI
  clients. Surfaces may localize copy, but must not flatten the error into a
  generic string.
- Sensitive domains must avoid leaking entity existence through overly specific errors.

## 8. Authentication

### 8.1 Public

- No login required.
- No request signing required beyond HTTPS.

### 8.2 Member

- Use bearer access tokens.
- Access token must contain:
  - `sub`
  - `jti`
  - `type`
  - `iat`
  - `exp`
- Backend must verify both JWT validity and session activity in storage.

### 8.3 Admin

- Use bearer access tokens and/or secure cookie-backed refresh flow.
- Admin permissions must be enforced server-side through RBAC.

### 8.4 Member Password Login

Member login must use **email and password**. Email code challenges are reserved
for registration email verification and future recovery flows.

Required flow:

```text
POST /v1/member/auth/login
GET  /v1/member/auth/me
POST /v1/member/auth/logout
```

Recommended request/response contract:

`POST /v1/member/auth/login`

```json
{
  "email": "member@example.com",
  "password": "MemberPass123!"
}
```

Response:

```json
{
  "data": {
    "accessToken": "<member-access-token>",
    "expiresInSeconds": 2592000,
    "member": {
      "id": "member_123",
      "email": "member@example.com",
      "displayName": "Grace Lee",
      "status": "active"
    }
  },
  "meta": {}
}
```

Rules:

- Login returns a member session only for valid email/password credentials and an
  active member account.
- Password hashes stay on the backend. The API never returns password hashes.
- Registration, not login, owns email verification challenges.

Registration with email verification:

```text
POST /v1/member/auth/register
POST /v1/member/auth/verify-code
```

`POST /v1/member/auth/register` may return:

```json
{
  "data": {
    "status": "pending_email_verification",
    "codeRequest": {
      "accepted": true,
      "challengeId": "7b56a159-0b47-40f2-8149-f4df89af3026",
      "delivery": "email",
      "maskedEmail": "m***@example.com",
      "expiresInSeconds": 600,
      "resendAfterSeconds": 60,
      "devCode": "123456"
    }
  },
  "meta": {}
}
```

`POST /v1/member/auth/verify-code` request:

```json
{
  "challengeId": "7b56a159-0b47-40f2-8149-f4df89af3026",
  "code": "123456"
}
```

Rules:

- `devCode` must be returned only in non-production environments.
- `challengeId` identifies one registration email verification challenge.
- The backend must store only a hash of the code, never the clear code.
- The backend should rate limit by email and IP.
- Maximum attempts per challenge should be enforced.
- Expired, consumed, or over-attempted challenges must fail consistently.
- Successful registration verification creates the member profile, stores the
  password hash, and returns either a signed-in session or pending approval.

## 9. Signing and Signature Rules

### 9.1 Client-App Requests

Rules:

- Normal mobile/web/admin API requests do **not** require per-request HMAC signing.
- The project must rely on:
  - HTTPS
  - bearer token authentication where required
  - server-side authorization
  - request IDs
  - rate limiting

Reason:

- Secrets embedded in mobile clients are not trustworthy.
- HMAC request signing is appropriate for trusted server-to-server callers, not mobile apps.

### 9.2 JWT Signing

Rules:

- Member and admin access tokens must be signed server-side.
- V1 may use symmetric signing such as `HS256` with strong environment secrets.
- Signing secrets must not be shared with clients.
- Tokens must include `jti` and be backed by revocable session records.

### 9.3 Webhook Signature Verification

Rules:

- All webhook endpoints must verify provider signatures before processing.
- Signature verification failure must return `401` or `400` with
  `signature_invalid`.
- Webhook verification must happen before any business mutation.

Examples:

- Stripe: verify `Stripe-Signature`
- Future mail provider callbacks: verify provider-specific signed headers

### 9.4 Internal Service Signatures

If the project later introduces internal callbacks across services:

- use HMAC SHA-256
- include `X-Signature`
- include `X-Timestamp`
- include `X-Nonce`
- sign the canonical string:

```text
METHOD \n
PATH \n
TIMESTAMP \n
NONCE \n
SHA256(body)
```

Rules:

- reject stale timestamps
- reject replayed nonces
- rotate shared secrets

This is reserved for trusted server-to-server traffic only.

## 10. Canonical Mutation Rules

Every mutation endpoint must define:

- authentication class
- idempotency behavior
- audit behavior
- validation boundary

Required examples:

- `POST /v1/member/auth/login`
  - not idempotent by body
  - credential/audit aware
- `POST /v1/member/auth/verify-code`
  - registration challenge only
  - cannot bypass password login
- `PUT /v1/member/devices/push-token`
  - idempotent by `(member, installationId)`
- `POST /v1/admin/sermons/:sermonId/publish`
  - authenticated
  - RBAC protected
  - audit logged
- `POST /v1/webhooks/giving/stripe`
  - signature verified
  - idempotent by provider event ID

## 11. Pagination

Rules:

- Cursor pagination is default for unbounded collections.
- Request shape:

```text
GET /v1/sermons?limit=20&cursor=<cursor>
```

- Response shape:

```json
{
  "data": {
    "items": [],
    "nextCursor": null
  },
  "meta": {
    "pagination": {
      "limit": 20,
      "nextCursor": null
    }
  }
}
```

Rules:

- `limit` must be capped.
- `cursor` must be opaque to the client.
- Sorting field and cursor encoding must be stable.

## 12. Idempotency

`Idempotency-Key` must be required for:

- payment/session creation with external providers
- annual statement generation
- finance export jobs if retries can duplicate artifacts
- future write operations that may be retried by mobile clients on timeout

Server rules:

- store `(idempotency_key, route, actor, request_hash, response_snapshot)`
- return the original successful response for safe retries
- reject same key with different request hash using `idempotency_conflict`

## 13. Money and Financial Safety

Rules:

- use integer minor units only
- never trust client-declared payment success
- provider webhook is the source of truth
- financial mutations must be audit logged
- statement or receipt files must use private storage and signed URLs

## 14. File Upload and Download

Rules:

- Upload endpoints must document accepted content types and max size.
- Large uploads should use either direct binary upload or presigned URLs, not base64 in JSON.
- Private downloads must use authenticated streaming or signed URLs.
- Responses must include `Content-Type`, `Content-Length`, and range headers where relevant.

## 15. Locale and Translation Rules

Rules:

- `Accept-Language` controls UI copy and server-generated natural language.
- Explicit `translationId` controls Bible text payloads.
- Locale should not silently override requested translation content.

## 16. Privacy and Logging

Never log:

- access tokens
- refresh/session tokens
- verification codes
- raw payment secrets
- prayer request bodies
- full AI prompts or raw private notes

Safe to log:

- request ID
- route
- method
- status code
- latency
- non-sensitive entity IDs

Rules:

- auth endpoints must avoid user enumeration
- protected endpoints must follow least privilege
- sensitive mutations must be audit logged

## 17. Audit Requirements

Audit-log at minimum:

- admin login
- content publish/archive/delete
- prayer moderation changes
- viewing/exporting giving data
- annual statement generation
- push notification fanout triggers for high-sensitivity categories if added later

Recommended audit fields:

```text
id
actor_user_id
action
resource_type
resource_id
before_json
after_json
created_at
```

## 18. Compatibility Rules

Rules:

- additive response fields are allowed in the same version
- removing or renaming fields is breaking
- changing auth requirements is breaking
- changing error code semantics is breaking

When introducing a better flow:

- preserve old routes temporarily
- document deprecation
- add tests covering both behavior and shape

## 19. Repository Alignment Notes

Current repo alignment status:

- `docs/api.md`, `packages/api_contracts/src/auth.ts`, and backend member auth
  now agree on email/password login.
- Registration settings decide whether registration requires email verification.
- `POST /v1/member/auth/verify-code` verifies registration challenges by
  `challengeId` and `code`; it is not a login endpoint.
- `docs/privacy_security.md` uses the same wording: email/password login plus
  optional registration email verification controlled by backend settings.
